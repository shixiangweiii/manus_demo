# 三种引擎执行链路与评分根因代码分析

## 1. 分析范围与结论

本文分析 2026-08-01 三份“明天天气怎么样？”打分记录，并对照当前源码，覆盖以下三种编排引擎：

- `sequential + react + low`：66/100，任务结果 PASS；
- `todo + react + low`：53/100，任务结果 PASS，但生产质量 FAIL；
- `dag + react + low`：41/100，任务结果 FAIL。

`goal`、`workflow` 没有对应打分记录，不纳入本次三引擎比较。

核心结论不是“某一种编排范式天然更好”，而是三次运行暴露了三种不同的控制面缺陷：

1. **Sequential 的主要问题是过度编排。** 它能顺序完成任务，但简单天气查询被拆成三步，并固定经过 Planner、多个 ReAct Action、Reflector 和最终 synthesis；工具能力提示与真实配置不一致，又诱发无效 Shell/Python 路径，最终以 30,120 tokens、78.20 秒换来可用答案。
2. **TODO 的主要问题是失败经验不能跨重试形成有效策略，而且控制面与用户输出共用上下文。** 每次 TODO 重试都会重新启动一轮 ReAct，却只把泛化的“达到最大 iterations”交给 TODO review；真实工具错误没有进入 review。最终 synthesis 又复用了 TODO JSON 控制历史，直接造成 `needs_update` 泄漏。前两次失败占已记录 token 的 53.0%。
3. **DAG 的主要问题是状态机不支持“等待用户/部分成功/可恢复失败”。** 第一个 Action 已得到杭州候选值，但验收器因“未确认无误”判失败；失败处理随即级联跳过全部下游。Planner 生成的 `fallback_strategy` 没有任何执行语义，最终 synthesis 只看到“没有成功 Action”，于是丢失杭州候选值和待确认问题。
4. **三者共享的底层问题决定了分数上限。** 当前工具目录、提示词、运行配置没有形成一致的能力契约；ReAct 将任意非空自然语言当作 Action 成功；低 effort 把工具结果截断到 1,000 字符；没有结构化来源字段；trace 对 IP/经纬度没有专门脱敏；checkpoint 只能整任务重跑，不能从交互等待点恢复。

因此，当前优先级应是先修复跨引擎公共契约和 P0 控制流，再比较三种编排策略。仅调 prompt 或单独提高某引擎重试次数，容易让成本继续上升而不解决根因。

## 4. 公共端到端执行链路

```text
main.py
  -> cli.py 解析 run / engine / executor / effort
  -> build_runtime()
       -> 读取并校验 settings.toml
       -> 构造共享 LLMClient、ContextManager、ToolRegistry
       -> 注册 tracing / checkpoint / 可选 capability 工具
  -> AgentRuntime.run()
       -> TaskRequest + RunSettings
       -> EngineSelector / EffortPolicy / ExecutorSelector
       -> 汇集 knowledge / memory / evolution context
       -> 构造 ReactActionExecutor
       -> 构造 Sequential / TODO / DAG Engine
       -> Engine 将任务拆为 Action，并交给共用 ReAct 执行
       -> Engine 自己判断 success 并合成 answer
       -> 可选 output guardrail
       -> 保存顶层 checkpoint、发出 task_completed
```

关键源码：

- CLI 在 `cli.py` 的 `_run_command()` 中调用 `runtime.run()`；`run` 命令以非交互模式构造 runtime。
- `runtime/app.py:32-97` 完成选择、上下文汇集、Executor/Engine 构造、运行、输出防护和顶层 checkpoint。
- `runtime/app.py:277-319` 表明三种引擎共享同一个 ActionExecutor 类型与同一工具集合。
- `execution/react.py:54-79` 将引擎 Action 包装后委托给 `ReActEngine`。
- `react/engine.py:247-395` 是共享的 ReAct 循环。

## 5. 共用 ReAct 与工具层：三种引擎共同的分数上限

### 5.1 Action 的“成功”定义过弱

`react/engine.py:326-358` 的逻辑是：当模型不再调用工具且返回任意非空文本，就生成 `success=True`。它没有判断该文本是：

- 已完成结果；
- 请求用户确认；
- “我还需要继续查询”；
- 泛化失败说明；
- 内部控制 JSON。

这会造成两类后果：

1. TODO 可以把形式上结束的自然语言当成已完成 TODO；
2. DAG 必须额外用一次 LLM 验收每个节点，既增加成本，又把“等待用户”压扁成 true/false。

应把 Action 结果从单一 `success: bool` 扩展成至少 `COMPLETED / PARTIAL / WAITING_USER / RETRYABLE_ERROR / TERMINAL_ERROR`，并把证据、待确认问题和失败类别作为结构化字段传给编排器。

### 5.2 能力说明与真实工具注册不一致

当前 `python_mode=disabled`，`tools/registry.py:62-72` 不会注册 `execute_python`。但：

- Planner prompt 在 `agents/planner.py:41-43`、`agents/planner.py:104-106` 告诉模型 Executor 可用 `execute_python`；
- `tools/web_search.py:46-55` 仍建议天气 JSON 使用 `execute_python`；
- `tools/shell_tool.py:53-65` 即使在 restricted 模式仍提示“调用 Python 时使用 python3”。

TODO trace 直接显示模型受该说明影响，尝试通过 `execute_shell` 运行 Python 请求天气 API。能力目录应由实际 `ToolRegistry` 和安全模式动态生成，而不是在多个 prompt/description 中静态写死。

### 5.3 工具失败路由只能“提示”，不能形成能力负缓存

`tools/router.py:92-161` 只按 `node_id + tool_name` 统计连续失败，并在阈值达到后给出软提示：考虑其他工具。问题包括：

- 不区分“参数错误”“策略禁止”“网络超时”“权限永久不可用”；
- 不阻止再次选择已经被策略明确拒绝的同类能力；
- 任意一次成功会清零连续失败。例如 `echo test` 成功会掩盖“Shell 不能运行 Python”的能力失败；
- `react/engine.py:252-275` 虽然计算了 router hint，但重试 Action 的第 1 iteration 使用原始 prompt，不会注入 hint；模型可先重复一次旧错误，第二轮才看到提示；
- 搜索收敛只统计当前 Action 的 `tool_calls_log`，TODO 新一轮重试会重新从 0 计数。

应在 run 级维护结构化能力状态，例如 `python_execution=unavailable(policy)`，让 Planner、TODO review 与每轮 ReAct 首个 prompt 都能看到；对策略拒绝类错误应默认禁止等价重试。

### 5.4 low effort 的 1,000 字符截断直接损害结构化数据使用

`react/engine_helpers.py:56-61` 将 low effort 的工具结果上限设为基础值一半，即当前 1,000 字符；`react/tool_call_helpers.py:88-115` 截断后只返回前缀。与此同时，`fetch_url` 自己允许抓取至 10,000 字符。

天气 JSON 的目标日期通常位于较后位置，所以本次 TODO 多次看到截断结果后重复抓取，仍无法形成目标日期的完整字段证据。这个机制同时解释了：

- TODO 的重复 `wttr.in` 请求与成本上升；
- Sequential/TODO 对“目标日期交叉验证”的证据不足；
- trace 中工具结果不能完整复核。

更合适的方向不是简单放大上下文，而是提供字段投影/JSONPath、内容分段、专用结构化数据工具，或让工具返回 `target_date + fields + source_url + fetched_at` 的小型证据对象。

### 5.5 隐私与 trace 脱敏仍不完整

`tools/user_location.py:45-49` 的首选 IP 定位服务使用 `http://ip-api.com/json/`；当前还设置 `location_ssl_verify=false`。虽然当前 `UserLocationTool` 面向模型只返回城市级结果，但其他工具抓取的原始定位响应仍可能进入 Action 上下文和 trace。

`core/redaction.py:23-30` 只识别 Bearer、常见密钥和口令形式，没有 IPv4/IPv6、经纬度或精确位置字段规则。这与 Sequential 报告中“完整 IP 和精确坐标进入 trace”的扣分一致。

应优先做到：默认询问或显式授权位置；强制 HTTPS 和证书校验；工具边界只向编排器暴露城市级值；trace exporter 对 IP、坐标和位置键做结构化脱敏。

### 5.6 缺少结构化 grounding 契约

三种引擎都把 Action 结果当作自由文本拼接。没有统一要求返回：

- 目标日期；
- 字段值；
- 来源 URL/provider；
- 抓取时间；
- 该来源是否直接覆盖目标日期；
- 来源之间是否真正独立；
- 不确定性与冲突字段。

因此 Reflector 只能评估已经经过模型概括的文本，无法可靠判断“两个来源是否独立”或“某字段是否由原始数据支持”。

## 6. Sequential：执行链路、66 分原因与代码问题

### 6.1 实际链路

```text
Planner.create_plan()
  -> 生成 3 个顺序步骤：定位 -> 查天气 -> 汇总
  -> 对每个 Step 调共用 ReActActionExecutor
       -> Action 1：多条定位路径，最终得到杭州
       -> Action 2：搜索/抓取天气，形成主要天气答案
       -> Action 3：再次汇总
  -> Reflector.reflect()
  -> TaskEngine.synthesize()
  -> EngineResult(success = 当前步骤全成功 AND reflection.passed)
```

对应源码为 `engines/sequential.py:17-109`。

### 6.2 为什么是 66 分

打分记录分项为：

| 维度 | 得分 | 直接原因 |
|---|---:|---|
| 任务完成与最终体验 | 22/25 | 最终有日期、杭州、天气、温度与不确定性 |
| 事实与证据 | 13/20 | 目标日期核心预报有支撑，但 `wttr.in` 交叉验证表述超过证据，来源独立性不明 |
| 规划与推理 | 12/15 | 日期和依赖正确，能保留温度冲突；部分来源推断过强 |
| 工具与恢复 | 10/15 | 从 Shell 失败恢复，但重复受限命令并写无效脚本 |
| 效率 | 3/10 | 30,120 tokens、12 次 LLM、78.20 秒，和任务复杂度不匹配 |
| 安全与隐私 | 3/10 | 最终未显示精确位置，但内部 trace 保存了完整 IP/坐标 |
| 可审计性 | 3/5 | 有 usage/耗时，但工具原始响应缺失、prompt 截断 |

66 分的本质是：**任务答案可用，所以结果类分数较高；但工具策略、成本、隐私和 grounding 同时拉低工程分。**

### 6.3 当前代码中的可优化点

#### A. Planner 对简单任务仍强制 2-6 步

`agents/planner.py:35-77` 要求 2-6 个步骤。天气任务因此容易被拆为“定位、查询、汇总”，而 Action 2 已经形成可交付答案后，Action 3、Reflector 和 synthesis 仍继续。本次额外三层消耗 8,057 tokens，占总量 26.7%。

建议让 low-effort bounded lookup 支持 1 步或 2 步快速路径，并以结构化完成条件决定是否需要单独汇总。

#### B. Sequential 并未真正执行 `dependencies`

`engines/sequential.py:41-57` 只是按 `plan.steps` 数组顺序执行，`Step.dependencies` 没有被调度器检查。如果 Planner 返回乱序或无效依赖，Sequential 仍照数组执行。本次计划恰好顺序正确，所以没有扣成任务失败，但这是一般性健壮性缺口。

#### C. Step 没有独立成功标准

Sequential 构造 Action 时只传 `id` 和 `description`（`engines/sequential.py:41-48`），没有像 DAG 那样传 `success_criteria`。所以每步成功完全依赖 ReAct 的“停止调用工具并输出文本”。最终 Reflector 再做一次粗粒度兜底，成本高且反馈晚。

#### D. 反思和最终合成重复，且 Judge 不独立

`engines/sequential.py:59-96` 固定调用 Reflector 后再 synthesis。Reflector 与 Planner、Executor、synthesis 使用同一个 LLM，只看到每步前 800 字符和工具名摘要（`agents/reflector.py:272-308`），看不到完整工具证据。因而运行时的 0.95 更像同模型自信度，不是独立质量分。

#### E. 重规划上下文存在不一致风险

重规划器看到 `all_results`，但下一次 Reflector 只收到当前新 plan 的 `current_results`；最终 synthesis 又拼接全部历史结果，包括可能失败或过时的输出。这会造成“反思看不全已完成工作、最终回答却混入旧失败结果”的双向不一致。本次没有触发重规划，但代码路径存在。

## 7. TODO：执行链路、53 分原因与代码问题

### 7.1 实际链路

```text
EmergentPlanner._init_todo_list()
  -> TODO 1：识别城市
  -> TODO 2：查询天气，依赖 TODO 1
  -> 外层 while(has_pending)
       -> 为 ready TODO 启动一轮 ReAct（low 最多 5 iterations）
       -> success：标 completed
       -> failure：retry_count + 1；最多 3 次
       -> 失败或阶段末尾时 _update_todo_list()
  -> _compile_answer() 使用同一个 EmergentPlanner 会话做最终合成
  -> TodoEngine 仅按所有 TODO 是否 completed 判顶层 success
```

对应源码：`engines/todo.py:16-53`、`agents/emergent_planner.py:234-374`。

### 7.2 为什么是 53 分

| 维度 | 得分 | 直接原因 |
|---|---:|---|
| 任务完成与最终体验 | 18/25 | 最终给出天气，但开头泄漏内部 `needs_update` JSON |
| 事实与证据 | 10/20 | 核心结果主要来自一次搜索；多次 `wttr.in` 没有完整覆盖目标日 |
| 规划与推理 | 7/15 | 初始 TODO 合理，但失败后不改策略、重复验证已知日期 |
| 工具与恢复 | 6/15 | 第三轮恢复成功；前两轮失败、4 次工具错误、无效脚本/echo |
| 效率 | 1/10 | 54,322+ tokens、21 次 LLM、17 次工具、117.38 秒 |
| 安全与隐私 | 8/10 | 只保留城市级近似定位；仍为未确认的自动定位 |
| 可审计性 | 3/5 | usage 与异常齐全；工具结果和 prompt 截断 |

前两次失败天气 TODO 消耗 28,809 tokens，占已记录总量 53.0%。所以 53 分的核心不是“最终没答案”，而是**以重试风暴、证据不足和输出协议泄漏换来了答案**。

### 7.3 当前代码直接解释的根因

#### A. TODO review 看不到真正失败原因

ReAct 达到上限时只返回：`Task did not complete within 5 iterations.`（`react/engine.py:388-395`）。`_update_todo_list()` 只把 `last_result.output[:2000]` 放入 review prompt（`agents/emergent_planner.py:584-614`），没有包含 `tool_calls_log`、策略拒绝类别或 run 级能力状态。

因此 review 只知道“TODO 没完成”，不知道：

- Python 被 restricted shell 策略禁止；
- 相同路线已经失败几次；
- 哪些 URL/字段已经抓到；
- 下一轮应该禁用什么能力。

这直接解释两次 `needs_update=false`：Planner 在做“TODO 描述是否还成立”的状态 review，不具备“执行策略必须改变”的证据。

#### B. 每次重试从头启动 ReAct，失败轨迹不进入新 Action

`agents/emergent_planner.py:687-727` 为同一个 TODO 重新调用 ActionExecutor，但只传 TODO 描述和依赖结果；之前失败尝试的工具轨迹不会进入新 ReAct 消息。ToolRouter 虽保留按 node 的计数，但第一个 iteration 看不到 router hint，且提示不具强制性。

结果是“重试完整 Action”，不是“从失败点带约束继续”。

#### C. 依赖结果被重复注入两次

`_execute_todo()` 先把依赖结果拼进 `prompt`（`agents/emergent_planner.py:707-714`），又把同一内容作为 `dependency_context` 传给 ActionExecutor（`agents/emergent_planner.py:721-726`）。`ReActEngine` 再追加 `Context from previous steps`（`react/engine.py:222-224`）。

TODO trace 明确显示 TODO 1 的长篇杭州定位结果在 TODO 2 首个 prompt 中出现两遍。这是纯粹的上下文放大，也会让每轮重试重复承担相同 token。

#### D. 成功后的失败记录没有被“已恢复”语义消解

`_compile_answer()` 把所有历史 `not r.success` 都放入 `blocked_step_results`，即使同一个 TODO 后来成功，也仍作为 `Blocked/failed TODOs` 注入最终摘要（`agents/emergent_planner.py:972-1007`）。这会把已恢复的中间失败与最终状态混在一起。

应按 `todo_id` 聚合最终状态，保留 attempt 轨迹供审计，但不给用户 synthesis 注入已经恢复的失败摘要。

#### E. 控制面历史直接污染最终 synthesis

这是 TODO 最终 JSON 泄漏的确定性代码路径：

1. `_update_todo_list()` 使用 `self.think_json()` 要求 `needs_update` JSON；
2. `BaseAgent.think_json()` 会把控制 prompt 和返回值保留在同一 `_messages` 历史（`agents/base.py:112-129`）；
3. 本次最后一次 JSON 响应使用 Python 字典语法，`chat_json()` 解析失败；失败的“请返回 JSON”用户消息已经写入历史，但没有匹配的 assistant 消息；
4. `_compile_answer()` 未调用 `reset()`，直接用同一个 `self.think()` 要求回答用户（`agents/emergent_planner.py:1009-1015`）；
5. 模型同时看到上一条“输出 JSON”和当前“回答用户”，于是先输出 `needs_update` JSON，再输出天气。

控制协议必须使用独立会话/结构化通道；最终合成必须只接收经过筛选的数据面结果。

#### F. 顶层 success 无法反映内部错误和输出合规

`engines/todo.py:41-44` 只要所有 TODO 最终为 completed 就判 `success=True`，不检查：

- 是否发生过内部 LLM/tool 错误；
- 最终答案是否泄漏控制字段；
- grounding 是否完整；
- 成本是否超预算。

所以本次顶层 span 为 OK，与生产质量 FAIL 并不矛盾。需要拆分 `task_success`、`process_health`、`output_schema_valid`、`grounding_valid`、`budget_ok`。

## 8. DAG：执行链路、41 分原因与代码问题

### 8.1 实际链路

```text
Planner.create_dag()
  -> Goal / SubGoal / Action 三层图
  -> DAGExecutor super-step
       -> 执行第一个 Action：获取城市
       -> ReAct 返回杭州近似定位 + 请求用户确认
       -> Reflector.validate_exit_criteria() 判“未确认无误”
       -> Action FAILED -> SKIPPED
       -> mark_subtree_skipped() 级联跳过天气和建议节点
  -> Reflector.reflect_dag() 得到 0.30 / NEEDS REWORK
  -> _compile_output() 只收 COMPLETED Action，得到固定失败串
  -> synthesis 基于该失败串生成泛化拒绝
```

对应源码：`engines/dag_engine.py:53-115`、`dag/executor.py:125-293`。

### 8.2 为什么是 41 分

| 维度 | 得分 | 直接原因 |
|---|---:|---|
| 任务完成与最终体验 | 5/25 | 没回答天气，也没把城市确认问题呈现给用户 |
| 事实与证据 | 7/20 | 杭州候选有工具来源且标近似，但没有任何天气事实 |
| 规划与推理 | 7/15 | 日期与高层依赖正确；退出条件过严，fallback 未执行 |
| 工具与恢复 | 5/15 | 定位工具有降级结果，但没有继续、重规划或等待用户 |
| 效率 | 6/10 | 仅 9,519 tokens/44.08 秒，但任务失败，72% token 在控制层 |
| 安全与隐私 | 8/10 | 没把近似定位冒充确定位置；仍缺自动定位授权 |
| 可审计性 | 3/5 | 顶层状态如实失败；prompt/DAG/provider 链路截断 |

DAG 的低 token 不是有效效率优势，因为它在第一个 Action 后就终止了实际任务。41 分主要由任务失败决定。

### 8.3 当前代码直接解释的根因

#### A. Planner 生成 fallback，但 Executor 从不执行

Planner 把 `fallback_strategy` 保存进 `TaskNode.risk`（`agents/planner.py:700-712`；`dag/models.py:41-58`）。全仓搜索显示 DAGExecutor 的失败路径没有读取该字段。

`dag/executor.py:386-439` 的实际失败处理只有：

1. 可选 rollback；
2. 把失败节点转为 SKIPPED/ROLLED_BACK；
3. `mark_subtree_skipped()` 跳过全部下游。

所以“显式询问用户”“用 web search 备选”等 fallback 目前只是给人看的文本，不是可执行分支。

#### B. 缺少 `WAITING_USER`，确认请求被压成 FAILED

`dag/models.py:19-26` 的状态只有 PENDING/READY/RUNNING/COMPLETED/FAILED/SKIPPED/ROLLED_BACK，没有 `WAITING_USER` 或 `PARTIAL`。而 `run` 命令是非交互 runtime，当前 `hitl=false`；`runtime/factory.py:129-152` 只有 `hitl and interactive` 时才注册 `ask_user`。

因此 Action 的“请确认是否在杭州”既无法真正等待，也不能成为可恢复状态，只能被退出条件验收为 false。

#### C. 验收失败会无条件级联跳过下游

`dag/executor.py:231-252` 把退出条件 false 当普通失败，随后 `_handle_failure()`；`dag/graph.py:185-198` 将所有下游 PENDING/READY 节点设为 SKIPPED。天气与建议节点因此没有任何执行机会。

应根据失败类别路由：

- `WAITING_USER`：保存 checkpoint 并返回澄清问题；
- `PARTIAL_LOW_RISK`：带免责声明继续；
- `RETRYABLE_TOOL_ERROR`：执行替代工具；
- `TERMINAL_ERROR`：才级联跳过。

#### D. 自适应规划在该失败场景实际不会启动

自适应规划要求至少有一个 completed Action 且仍有 pending Action（`dag/executor.py:665-686`）。本次第一个 Action 验收失败，完成 Action 数为 0；失败处理又把下游全部跳过，所以条件不成立。

虽然 `PlannerAgent` 有 `replan_subtree()`，`DagEngine/DAGExecutor` 的失败处理并未调用它。当前“adaptive_planning=true”不能覆盖首次 Action 验收失败这一关键场景。

#### E. 最终合成主动丢弃部分结果和反思建议

`dag/executor.py:634-658` 只汇总 `NodeStatus.COMPLETED` 的 Action；没有成功 Action 就返回固定串 `No action nodes completed successfully.`。杭州候选、近似置信度、待确认问题均被丢弃。

随后 `engines/dag_engine.py:87-89` 虽然已经得到了完整 DAG reflection，却只把 `raw` 传给 synthesis，没有传 `reflection.feedback/suggestions`。这正是最终回答错误地说“无法获取天气”，而不是“我近似定位到杭州，请确认城市”的代码原因。

#### F. 当前配置使 DAG 承担图成本却没有并行收益

`settings.toml` 中 `dag_serial_execution=true`，`dag/executor.py:176-206` 每个 super-step 只执行一个 Action。对当前线性天气链路，DAG 仍要付出三层 Planner 和逐 Action LLM 验收成本，却不能并行。

这不是本次任务失败的主因，但说明自动选择 DAG 时需要同时考虑“是否真的存在可并行分支”和当前串并行配置。

#### G. checkpoint 不能恢复到 DAG 中间状态

Runtime checkpoint 模型明确写着“resume restarts the task”（`checkpoint/models.py:29-46`）；`runtime/app.py:243-275` 也只是用同一 task/engine/executor/effort 重新调用 `run()`。DAG 内部 `save_checkpoint()` 没有连接到本次 `DagEngine` 的持久化回调。

因此即便新增 `WAITING_USER`，还需要真正持久化 DAG nodes/state/results/待回答 prompt，才能在用户回复后从断点继续，而不是重新定位、重新规划。

## 9. 三种引擎的横向架构问题

| 问题 | Sequential | TODO | DAG | 影响 |
|---|---|---|---|---|
| 任意非空文本即 Action 成功 | 有 | 有 | 由额外验收兜底 | 成功语义不稳、DAG 成本高 |
| Prompt 与真实工具能力不一致 | 有 | 有 | 有 | 诱发 Python/Shell 错路 |
| 失败类别不结构化 | 有 | **最严重** | **最严重** | 无法做正确重试/fallback |
| 控制面与用户输出隔离 | 较好 | **失败** | 最终输入丢信息 | JSON 泄漏或泛化拒绝 |
| 结构化证据/来源链 | 无 | 无 | 无 | grounding 分数低 |
| 简单任务预算/快速路径 | 无 | 无 | 无 | 成本与复杂度不匹配 |
| 真正可恢复 checkpoint | 无 | TODO 类内有接口但 runtime 未接通 | 无 | 等待用户/中断后整任务重跑 |
| success 健康度分层 | 无 | 无 | 无 | 顶层 OK/ERROR 信息过粗 |
| 位置隐私与 PII trace 防护 | 共用缺陷 | 共用缺陷 | 共用缺陷 | 安全与分享风险 |

三种引擎的 success 判定还不一致：

- Sequential：当前轮 Action 全成功且最终 Reflector passed；
- TODO：所有 TODO 状态 completed；
- DAG：图 complete、有 completed Action、没有任何 failed_action_id、最终 Reflector passed。

所以内部 success 不能直接用于公平比较；评测应继续以统一的外部任务完成、输出合规、grounding、过程健康、预算和安全 gate 为准。

## 10. 建议优先级（仅分析，不实施）

### P0-1：建立统一的结构化 ActionOutcome

建议字段：

```text
status: COMPLETED | PARTIAL | WAITING_USER | RETRYABLE_ERROR | TERMINAL_ERROR
answer_or_result
evidence[]: {source, url, fetched_at, target_date, fields, confidence}
blocking_reason
question_for_user
failure_class: policy | permission | timeout | network | parse | model
forbidden_capabilities[]
next_strategy
```

这一个改动方向能同时改善 TODO 重试、DAG 等待/恢复、Sequential 验收和统一评测口径。

### P0-2：隔离控制面与用户数据面

- TODO init/update/review 使用独立的 JSON 会话或严格 schema 通道；
- 最终 synthesis 新建干净会话，只输入已筛选的成功结果与未解决阻塞；
- 输出前做确定性协议检查，禁止 `needs_update`、TODO IDs、内部状态对象进入用户答案；
- DAG synthesis 同时接收 completed、partial、waiting、failed summary 和 reflector 建议，而不是只接 completed raw。

### P0-3：让 DAG fallback 与 WAITING_USER 成为可执行状态

- 不再把所有退出条件 false 统一当终止失败；
- 把 fallback 编译成明确路由：`ask_user / continue_with_caveat / retry_alternate / replan_subtree / fail`；
- `run` 非交互场景若无法等待，应直接把可行动问题作为最终答案，并保留可恢复 checkpoint；
- 低风险天气类任务允许“以杭州近似位置继续 + 明确免责声明”，不要求区县确认。

### P0-4：按实际配置生成能力契约，并对策略拒绝做硬负缓存

- 从 ToolRegistry 动态生成 Planner/ReAct 能力说明；
- `python_mode=disabled` 时不出现 `execute_python` 建议；
- restricted shell 描述明确“Python 不可执行”，不再提示 python3；
- 首次 policy rejection 后将能力标记为当前 run 不可用，后续 Planner/ReAct 首轮均可见并禁止等价重试。

### P0-5：补齐定位隐私与 trace 脱敏

- 去掉明文 HTTP 定位 provider；
- 默认开启 TLS 校验；
- 自动 IP 定位改为明确产品授权或用户 opt-in；
- trace 对 IP、坐标、Cookie、Token 和精确位置字段做结构化脱敏；
- 日志和 trace 只传播城市级最小必要信息。

### P1-1：给 TODO 重试传递失败策略，而不是只传“没完成”

- review 输入包含最后 attempt 的结构化错误、工具调用摘要、已获取证据和禁止能力；
- 同一 TODO 的下一 attempt 必须有 `strategy_delta`；没有变化则不允许完整重跑；
- 失败尝试按 todo_id 聚合，成功恢复后不再注入“blocked”用户摘要；
- 对 token、LLM、工具和墙钟设总预算，超过预算降级而不是继续重试。

### P1-2：为低风险短查询提供快速路径

可采用通用路由而非硬编码题目：

```text
短、单实体、实时查询
  -> 获取/确认必要上下文
  -> 一个结构化实时数据工具
  -> 可选一次独立复核
  -> 直接模板化输出
```

Sequential 可减少 Planner/汇总层；TODO 可减少完整 Action 重试；DAG 不应在纯线性短任务上默认使用三层图。

### P1-3：提供结构化实时数据/字段投影能力

天气可以先作为验证场景，但设计应通用：

- `fetch_url` 支持 JSONPath/字段投影/分页；或
- 提供 typed connector，返回目标日期字段、URL、时间戳和 provider；
- 不要让模型为解析 10KB JSON 临时写脚本；
- 来源冲突要按来源分别呈现，不能合并为伪范围 `37~39℃`。

### P1-4：统一成功、健康与预算门禁

建议至少分开：

- `task_success`：是否回答用户问题；
- `output_valid`：格式与内部字段隔离；
- `grounding_valid`：关键字段是否有证据；
- `process_health`：是否有未恢复内部错误；
- `budget_ok`：token/延迟/工具数是否合规；
- `privacy_ok`：是否满足最小化和脱敏。

顶层状态可有 `SUCCESS / SUCCESS_WITH_WARNINGS / WAITING_USER / FAILED`，避免 TODO 本次“顶层 OK 但生产质量失败”的信息损失。

### P2：真正的持久化恢复与可审计 trace

- checkpoint 保存引擎语义状态，而不只是 task/engine 参数；
- trace 保存脱敏、定长的工具输入/输出摘要，并链接到独立 artifact/hash；
- provider fallback 生成子 span，区分外层工具成功和内部 provider 退化；
- 明确记录截断标志、原始长度与可定位 artifact。

## 11. 建议的验证顺序

不要直接用同一条天气题反复调 prompt。建议建立固定 replay 评测，避免过拟合：

1. **确定性组件测试**
   - Python disabled 时，所有 prompt/schema 中均不出现可执行 Python 建议；
   - policy rejection 后，相同/等价能力不再调用；
   - TODO 依赖结果只注入一次；
   - TODO 最终答案不含 `needs_update` 等控制字段；
   - DAG partial/waiting 信息进入最终用户输出；
   - IP/坐标在 trace 中被脱敏。
2. **固定工具响应 replay**
   - 正常天气；
   - 定位近似且需确认；
   - 定位失败；
   - 天气主源失败、备用源成功；
   - 长 JSON 中目标日期位于截断区；
   - 两来源字段冲突。
3. **三引擎重复运行**
   - 每个 case 每引擎至少多次运行；
   - 报告成功率、输出合规率、grounding、P50/P95 延迟、token、工具失败与恢复率；
   - Sequential/TODO/DAG 使用同一 replay 和相同预算。
4. **隐藏任务集与 OOD**
   - 除天气外覆盖新闻、汇率、本地搜索、文件任务、需要澄清的高风险任务；
   - 验证改动修复的是通用控制语义，而不是天气关键词特判。

## 12. 最终判断

当前三种引擎可以概括为：

- **Sequential：目前最能完成这个短任务，但成本、工具策略、grounding 和隐私不合格；66 分来自“结果可用、过程偏重”。**
- **TODO：具备最终恢复能力，但重试没有策略记忆，且控制/输出上下文混用；53 分来自“答案完成、工程过程明显退化”。**
- **DAG：规划与安全意识并非完全错误，真正失败在状态机和恢复语义；41 分来自“部分信息已获得，但被错误地转成不可恢复失败”。**

最值得先做的不是选出“赢家”，而是统一四个公共基础：

1. 结构化 ActionOutcome 与失败分类；
2. 实际能力驱动的工具契约和 run 级负缓存；
3. 控制面/用户输出隔离；
4. WAITING_USER、部分结果与真正 checkpoint 恢复。

这些基础完成后，再通过固定 replay 和多次运行比较三种编排器，分数才更能反映编排策略本身，而不是底层协议缺陷。
