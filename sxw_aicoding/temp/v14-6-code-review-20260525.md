# v14.6 Evaluation Harness Code Review

> Date: 2026-05-25
> Scope: v14.6 evaluation-related implementation after roadmap update
> Reviewed areas: `evaluation/`, `tests/test_evaluation.py`, `conftest.py`, relevant tool registration in `main.py`

## Summary

v14.6 has the right structural direction: benchmark expansion, `EvaluationProbe` extraction, verifier module, baseline module, and CLI baseline flags are present. The benchmark set has expanded to 38 tasks and the pure syntax check passes.

However, several core acceptance criteria are not fully wired yet. The most important issue is that deterministic verifiers exist as a module but are not invoked by the evaluation result path, so v14.6.3 is currently mostly declarative. The second important issue is that the evaluation runner does not register `fetch_url`, which invalidates the new web+fetch task coverage. The third issue is that the promised lightweight dry-run/offline eval behavior still fails in a bare environment because `rich` is imported at module load time.

## Findings

### P0 - Deterministic verifiers are dead code

Evidence:

- `BenchmarkTask.verifiers` is defined in `evaluation/benchmark.py:79`.
- `run_verifiers()` is implemented in `evaluation/verifiers.py:400`.
- Safety benchmark tasks define verifier specs, for example `safety_001` in `evaluation/benchmark.py:682`.
- No code path calls `run_verifiers()` outside `evaluation/verifiers.py`.
- `EvaluationProbe.build_result()` still decides task success using only `self.task_success`, `must_include_keywords`, and `must_not_include` in `evaluation/probe.py:480`.

Impact:

The v14.6.3 Outcome Verifier capability is not active. File, JSON field, numeric range, regex, and safety verifier specs do not affect pass/fail. This undermines the main goal of making evaluation more deterministic and less keyword-only.

Suggested fix:

- Add verifier result fields to `TaskEvaluationResult`, or at least attach verifier detail into `failures` / `config_snapshot`.
- In `EvaluationProbe.build_result()` or `EvaluationRunner.evaluate_task()`, call `run_verifiers(task.verifiers, final_answer, sandbox_dir)`.
- If any actionable verifier fails, set `execution.task_success=False` and recompute `execution_score` / `overall_score`.
- Keep LLM-as-Judge as fallback only when no deterministic verifier exists or all deterministic verifiers are skipped.

### P0 - `fetch_url` benchmark tasks cannot exercise `fetch_url`

Evidence:

- `EvaluationRunner` default tools are created in `evaluation/runner.py:93`.
- The default tool list includes `WebSearchTool`, `UserLocationTool`, `CodeExecutorTool`, `FileOpsTool`, and `ShellTool`, but not `FetchUrlTool`.
- The real application registers `FetchUrlTool` in `main.py:661`.
- New benchmark task `easy_006` expects `fetch_url` in `evaluation/benchmark.py:445`.

Impact:

The v14.6 web+fetch benchmark expansion cannot test the intended tool path. Tasks tagged `fetch` will run in an environment where the expected tool is unavailable, so failures may measure tool registration mismatch rather than agent capability.

Suggested fix:

- Add `FetchUrlTool` to `EvaluationRunner`'s default tool list.
- Prefer extracting a shared base-tool factory used by both `main.py` and `evaluation/runner.py`, to avoid future drift.
- Add a unit test that compares evaluation runner base tool names with the main runtime base tool set, or at least asserts `fetch_url` is present.

### P1 - Lightweight dry-run and offline evaluation tests still fail without `rich`

Evidence:

- `evaluation/eval_cli.py:37` imports `rich` at module load time.
- `evaluation/eval_cli.py:44` imports `evaluation.report`, which imports `rich` at `evaluation/report.py:20`.
- `python3 -m evaluation.eval_cli --dry-run` currently fails with `ModuleNotFoundError: No module named 'rich'`.
- `python3 -m pytest tests/test_evaluation.py -q -o asyncio_mode=auto` currently reports `50 passed, 1 failed`; the failing test imports `evaluation.report` and hits missing `rich`.

Impact:

The roadmap requirement that dry-run and pure evaluation unit tests work in a minimal environment is not met. OpenAI runtime dependencies were decoupled from the probe path, but presentation dependencies still block dry-run and report smoke tests.

Suggested fix:

- Move `rich` imports behind a best-effort adapter or into functions that need rich output.
- Provide a plain-text fallback for `--dry-run` if `rich` is unavailable.
- Either make report smoke tests skip cleanly when `rich` is unavailable, or implement a no-rich fallback path.
- Avoid importing `evaluation.report` at CLI module load when the selected command is `--dry-run`.

### P1 - Baseline regression gate is effectively a no-op with the shipped baseline

Evidence:

- `evaluation/baselines/v14_6_initial.json` contains only an empty `modes` object.
- `compare_baseline()` iterates current modes and silently skips any missing baseline mode in `evaluation/baseline.py:124`.
- `RegressionThresholds` defines time and failure thresholds, but `compare_baseline()` currently enforces success rate, overall score, and token ratio only.

Impact:

`--baseline evaluation/baselines/v14_6_initial.json --fail-on-regression` cannot fail because there are no modes to compare. This gives a false sense that a regression gate exists.

Suggested fix:

- Ship either no baseline file until a real one exists, or mark the placeholder clearly as non-gating.
- Treat missing baseline modes as warning or regression when `--fail-on-regression` is enabled.
- Enforce `time_increase_ratio` and `failure_increase_ratio`, or remove those thresholds until implemented.
- Add tests for missing baseline modes, token regression, time regression, and failure-count regression.

### P1 - Reliability and tag reporting are declared but not wired

Evidence:

- `resume_success_rate` and `checkpoint_avg_count` are declared in `evaluation/metrics.py:338`, but not populated in `aggregate_results()`.
- Report output aggregates by difficulty in `evaluation/report.py:156`, but there is no tag matrix for HITL/SubAgent/GoalDriven/Resume/Safety.
- Benchmark expansion includes only two `resume` tasks and no real checkpoint/resume execution harness.
- `BENCHMARK_TAGS` includes `memory` and `rollback`, but there are no corresponding benchmark tasks.

Impact:

v14.6.5 reliability reporting is incomplete. Resume tasks currently behave like ordinary multi-step tasks, so the evaluation does not measure actual checkpoint/resume reliability.

Suggested fix:

- Add explicit resume evaluation scenarios that interrupt and resume through `TaskStateStore` / `OrchestratorAgent.resume()`.
- Capture checkpoint count, resume attempts, paused count, and resume success into `TaskEvaluationResult`.
- Add tag-level aggregation and report table for HITL, SubAgent, GoalDriven, Resume, Safety, Fetch, and Multi-file tasks.
- Either add memory/rollback tasks now or remove those tags from the canonical vocabulary until the task set exists.

## Recommended Fix Order

1. Wire deterministic verifiers into task success calculation and scoring.
2. Add `FetchUrlTool` to evaluation runner's default tool list, ideally via shared base-tool factory.
3. Make `--dry-run` and pure evaluation tests work without `rich`.
4. Make baseline gate non-empty and enforce missing mode/time/failure regressions.
5. Add real resume/checkpoint evaluation flow and tag-level reporting.

## Notes

The review ignored `__pycache__` and other generated noise in the working tree. The findings above are focused on v14.6 evaluation behavior and acceptance criteria.
