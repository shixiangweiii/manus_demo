### 3.3 TODO 1：位置识别

TODO 1 的执行相对合理：

- 第一次 LLM 决策即选择专用 `get_user_location`；
- 工具成功返回杭州；
- 中间结果明确说明位置来自 IP 近似定位，可能有城市周边偏差；
- trace 没有保存完整 IP 和精确经纬度。

但中间结果较冗长，还包含“请问是否还有下一个 TODO”等不适合内部依赖结果的交互语句。这些内容在后续 prompt 中被重复注入，增加了上下文开销。

### 3.4 TODO 2：第 1 次尝试

执行顺序：

1. 尝试用 `execute_shell` 运行内联 Python 请求 `wttr.in`，被受限策略拒绝；
2. 使用 `fetch_url` 成功取得较大的 JSON，但 Agent 判断输出被截断；
3. 使用 `file_ops` 写入 `weather.py`；
4. 再次尝试 `python3 weather.py`，仍被策略拒绝；
5. 再次用 `fetch_url` 请求人类可读天气文本；
6. 达到 5 iterations，Action 失败。

主要问题：第一次 Shell 已明确表明 Python 不可执行，后续仍写入脚本并再次尝试相同能力。

### 3.5 第 1 次 TODO review

EmergentPlanner 判断：

- TODO 1 已完成；
- TODO 2 尚未完成；
- 无需新增或修改 TODO；
- 继续执行 TODO 2。

该 review 只更新了完成状态，没有把“Shell/Python 在当前能力模式下不可用”固化成后续执行约束，因此未发挥策略反思作用。

### 3.6 TODO 2：第 2 次尝试

执行顺序：

1. 再次抓取同一 `wttr.in` JSON；
2. 请求多个 `wttr.in` 文本格式；
3. 运行与用户任务无关的 `echo test`；
4. 再次尝试内联 Python，第三次 Shell 失败；
5. 再次写入 `weather.py`；
6. 达到 5 iterations，Action 再次失败。

这一轮重复了第一轮已验证无效的路线。`echo test` 只证明一个简单 allowlisted 命令可以运行，不能证明 Python 能力可用，对天气任务没有实际贡献。

### 3.7 第 2 次 TODO review

第二次 review 仍返回 `needs_update: false`，没有：

- 将 Shell/Python 标记为不可用；
- 改写 TODO 2 为“仅使用 web_search/fetch_url”；
- 缩小所需天气字段；
- 阻止继续写入脚本；
- 在重试预算中考虑前两轮成本。

因此 TODO 引擎虽然具备状态 review 节点，但没有体现有效的策略自适应。

### 3.8 TODO 2：第 3 次尝试

执行顺序：

1. 调用 `date`，但系统上下文已经提供当前日期；该 Shell 调用失败；
2. 请求 `wttr.in` 文本；
3. 并行请求 `wttr.in` 两日文本和 `web_search`；
4. 搜索结果提供了 8 月 2 日杭州天气关键数据；
5. 再次请求 `wttr.in` JSON；
6. 在第 4 iteration 输出天气结果，Action 完成。

最终真正解决任务的核心证据来自第三轮的 `web_search`。多次 `wttr.in` 调用没有形成完整、可审计的目标日期结构化字段。

### 3.9 最终 TODO 更新与输出污染

Action 完成后，EmergentPlanner 尝试更新 TODO 列表，但 LLM 返回：

```text
{'needs_update': False, 'reason': '...'}
```

这不是合法 JSON，因为使用了 Python 单引号和 `False`，导致解析错误。

随后最终 synthesis 同时受到“返回 JSON”和“回答用户”两类要求影响，最终把内部控制数据输出给用户：

```json
{"needs_update": false, "reason": "TODO 1 和 TODO 2 均已完成，任务目标已达成，无需新增、修改或阻塞任何 TODO。"}
```

然后才输出正常的天气回答。内部 TODO 控制状态不应出现在用户界面中。

## 7. Grounding 与推理正确性分析

### 7.1 日期推理

系统 prompt 已明确注入：

```text

```

### 7.2 天气证据链

内部 thinking 已承认：

- `wttr.in` 文本主要显示 8 月 1 日；
- 两日文本被截断，未清楚显示第二天；

### 7.3 规划与策略反思

- 从策略拒绝中学习当前能力边界；
- 将失败原因写入下一轮上下文；
- 在重试前修改工具计划；
- 根据剩余预算决定是否继续重跑完整 Action；
- 将“状态 review”与“策略 review”区分开。

Planner 两次返回 `needs_update: false`，说明它只判断 TODO 描述是否仍然成立，没有判断执行方法是否必须改变。

## 12. 整改建议

### P0：隔离控制状态与用户输出

1. TODO 更新结果必须走结构化内部通道，不能进入最终用户 message；
2. JSON 解析失败时由确定性 fallback 修复或回退，不要让同一模型同时输出控制 JSON 和用户答案；
3. 最终输出前增加 schema/前缀检查，拒绝包含 `needs_update`、TODO IDs 等内部字段的用户答案；
4. 顶层任务状态应区分 `SUCCESS_WITH_INTERNAL_ERRORS` 与完全健康的 `OK`。

### P0：失败后更新能力状态

1. 第一次收到策略拒绝后，将 `execute_shell/python unavailable` 写入当前 run 的能力状态；
2. 后续 Planner 和 ReAct executor 必须接收该状态；
3. 禁止在同一任务中再次生成等价 Python 命令或脚本执行路径；
4. TODO review 不只判断描述是否改变，还必须输出下一轮允许和禁止使用的策略。

### P1：简单任务预算与快速路径

1. 为 `effort=low` 设置 LLM、tool、token 和墙钟预算；
2. 天气查询使用快速路径：`获取/确认城市 → 一次结构化天气查询 → 必要时一次独立复核 → 输出`；
3. 单个 TODO 达到 max iterations 后，下一轮不应从头重复完整历史；
4. 超过一次失败重试后应降级为向用户说明数据不可用，而不是继续无上限扩大成本。

### P1：结构化天气能力

1. 增加专用天气工具，直接返回目标日期的天气、温度、风向、风力和抓取时间；
2. 或让 `fetch_url` 支持 JSONPath/字段投影，避免 10,041 字符 JSON 被截断；
3. 如果 Python 模式关闭，不应建议通过 Python 解析公共 API；
4. 使用系统注入的当前日期，不再调用 `date` 或从网页反推日期。

### P1：Grounding 与来源链

1. 保存目标日期、来源 URL、抓取时间和原始字段摘要；
2. 区分搜索摘要、直接页面和独立数据提供商；
3. 只有两个来源都明确包含目标日期字段时才能称为交叉验证；
4. thinking 发现来源不完整或出现垃圾文本时，最终答案必须继承该不确定性；
5. 将 37℃ 与 39℃ 分别绑定到各自来源，不要组合成 `37~39℃` 的伪范围。

### P2：Trace 与评测

1. 工具 span 保存经过脱敏、长度受控的请求参数和结果摘要；
2. 记录所有失败 LLM 调用的 usage，或明确标记计费不可观测；
3. 增加多次运行，报告成功率、平均/中位延迟、token 分布和失败模式；
4. 对 sequential 与 todo 使用固定天气响应 replay，进行真正可重复的同条件比较；
5. 将结果成功、过程健康、成本、安全和格式合规拆成独立 gate。
