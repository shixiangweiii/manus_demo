## 一、总体结论

重构的设计原则（以行为命名、引擎与执行器分离、配置分层、统一结构化事件源、删除被替代旧路径、朴素 Python）**基本落地**；`docs/`（architecture / engines / configuration / evaluation）与 changelog 口径一致；六个子系统声明的大部分修复经核实属实。

本轮评审**未发现 P0**（崩溃 / 数据丢失 / 可直接利用的安全洞）。发现 **1 个 P1、11 个 P2、27 个 P3，以及 4 条跨切面主题**。最具价值的发现集中在两类：

1. **"声明已修复但实际只覆盖部分路径"**：取消路径仍让 Checkpoint 卡在 `running`；异步事件订阅在 loop teardown / no-loop 分支仍未真正安全；`log_prompts=false` 的回退与错误属性通道未门控。
2. **边缘场景误判**：DagEngine 把"条件跳过的节点"判为失败；Workflow `${...}` 模板无转义、把 shell `${HOME}` 当成步骤引用；shell 黑名单正则要求 `-f` 与其它标志合并书写，分开即绕过。

这些恰好落在重构文档"未在本轮宣称通过"的真实模型与正式评测区间，属可预期但应记录在案的工程缺陷。

> 严重度：P0 崩溃/数据丢失/安全洞；P1 真实场景下的错误行为或可绕过安全；P2 边缘场景错误或设计锋利边缘；P3 质量与次要。标注 **【已复验】** 表示主审独立读码/运行验证过。

### 🔴 P1

#### P1-1 Shell 黑名单绕过：`rm` 分开书写标志位即逃逸【已复验】
- **文件**：`tools/shell_tool.py:31-33`（`BLOCKED_PATTERNS[0]`），`guardrails/patterns.py:52`（`DANGEROUS_SHELL_PATTERNS` 同款正则）
- **问题**：正则 `r"\brm\s+(-[a-zA-Z]*f[a-zA-Z]*\s+|.*--no-preserve-root\s+)/"` 要求 `-f` 与其它标志**合并在一个选项 token** 内（如 `-rf`/`-fr`）。`-r` 与 `-f` 分开书写时不匹配。
- **失败场景**（已运行验证）：
  - `rm -rf /` → BLOCKED ✅
  - `rm -fr /` → BLOCKED ✅
  - `rm -r -f /` → **PASS（绕过）** ❌
  - `rm --recursive --force /` → **PASS** ❌
  - `rm -r -f ~` → **PASS** ❌
- **为何真实**：Guardrails 默认关闭（`capabilities.guardrails=False`，`core/settings.py:175`），shell 工具的黑名单是**默认且首要**防护；`shell_tool.py:138` 以 `["bash","-c",command]` 在用户账号下执行（cwd=沙箱，但绝对路径可达任意位置）。经 `web_search`/`fetch_url` 不可信输出触发提示注入的 LLM 可生成 `rm -r -f ~` 绕过黑名单。Guardrail 层同款正则，即便开启亦不拦。
- **建议**：改用更稳健的检测（如先词法拆分再判 `rm` + 任一破坏性标志组合），或对 `rm` 指向沙箱外路径一律拒绝；并与 Guardrail 共用同一判定函数，避免两份漂移。

### 🟠 P2

#### P2-1 EventBus 异步订阅在 loop teardown 静默丢事件
- **文件**：`core/events.py:108-122`
- **问题**：运行中 loop 分支用 `loop.create_task(...)` 调度异步订阅者后立即返回，调用方无法 await。当外层 `asyncio.run()` 在 `runtime.run()` 返回后拆解 loop 时，未完成的订阅任务被取消，`report_failure` 在 `done.cancelled()` 处提前返回、**连日志都不打**。
- **失败场景**：用户经 `subscribe_async` 注册一个在 `task_completed` 时 flush 缓冲/发 webhook 的订阅者；`runtime/app.py:92` emit 后于 `:93` 返回，顶层 `asyncio.run` 取消残留任务，`task_completed` 处理被静默丢弃。
- **为何真实**：changelog 第五节声称"异步事件订阅…处理不完整"已修，但 teardown 取消路径仍未处理（无日志、无 await、无 barrier）。当前潜伏——因所有在树订阅者（`TracingBridge`/`_Collector`/`EventBridge`）均为同步，今天不触发回归。

#### P2-2 无 loop 分支 `asyncio.run` 破坏共享异步资源
- **文件**：`core/events.py:99`
- **问题**：同步代码、无运行 loop 时，`_schedule_async_handler` 用全新临时 loop 经 `asyncio.run` 跑异步订阅者。绑定到其它 loop 的资源（如 `LLMClient` 的共享 `AsyncOpenAI`/httpx 客户端、asyncio 锁/信号量）会抛 `RuntimeError: ... attached to a different event loop`，且异常在 `:100-105` 被吞（仅 debug 日志）。
- **失败场景**：一个调用 `llm_client.chat(...)` 的异步订阅者被同步工具回调（主 loop 之外）触发 → `asyncio.run` 建临时 loop，客户端 transport 绑定到（已关闭的）主 loop → 调用时抛错被吞，事件丢失且无表面错误。
- **为何真实**：这是 changelog 声称已处理的"无事件循环"场景，但对任何触及 loop 绑定资源的订阅者都不安全——而本仓异步订阅者恰好都会触及。

#### P2-3 DagEngine 把"条件跳过的节点"判为失败【已复验】
- **文件**：`engines/dag_engine.py:88-90`
- **问题**：`success = bool(action_nodes) and all(n.status==NodeStatus.COMPLETED for n in action_nodes) and reflection.passed` 要求**所有**动作节点 `COMPLETED`。但条件边（`dag/executor.py:437-489` 的 `_process_conditions`）会合法地把分支/回退节点置为 `SKIPPED`（`dag/graph.py:269` 视其为终态）。`SKIPPED != COMPLETED` → `all(...)` 为 False。
- **失败场景**：LLM 规划的带条件分支 DAG——主路径成功、回退节点被 `SKIPPED` → `is_complete()=True` 但 `success=False`；即使 `reflection.passed=True`，结果仍判失败。`_compile_output`（`:616-640`）已只取 `COMPLETED` 节点，说明代码知道有些节点不会完成，但成功门未与之对齐。
- **为何真实**：条件边是已实现特性（`_evaluate_condition` 双模、`_process_conditions` 每超步运行）。任何 LLM 规划出条件/回退边的 DAG 都会误报失败。

#### P2-4 WorkflowEngine `${...}` 模板无转义；shell `${HOME}` 被误判为步骤引用【已复验】
- **文件**：`workflow/engine.py:16`（`_TEMPLATE_RE=r"\$\{([A-Za-z0-9_\-]+)\}"`）、`:203-227`（`_resolve_params`）
- **问题**：步骤 `params` 中每个 `${...}` 都被当作对它步输出的模板引用，无转义机制。工具参数若合法包含 `${VAR}`（shell 常见，如 `{"command":"export PATH=${HOME}/bin"}`），解析器在 `step_results` 找不到 `HOME` 即抛 `ValueError("unresolved workflow result(s): HOME")`，工具尚未执行就中断。
- **失败场景**：Workflow 步骤调用 shell 工具带 `{"command":"echo ${HOME}"}` → `_resolve_params` 找到 `${HOME}`、非步骤 ID → 抛错 → 以"未解析结果"误中断，而非执行命令。
- **为何真实**：`Error:` 工具输出约定（`react/tool_call_helpers.py:60`）确认 shell 工具是一等公民；shell `${VAR}` 语法无处不在，用户无从转义。

#### P2-5 `CheckpointStore.list_tasks()` 遇畸形文件名崩溃【已复验】
- **文件**：`checkpoint/store.py:55-61`、`:81-85`（`_path`）
- **问题**：`list_tasks` 遍历 `*.runtime.json` 调 `self.load(name.removesuffix(...))`；`load`→`_path` 在 `task_id` 含非 `[alnum/-/_]` 字符时抛 `ValueError`。`except` 仅捕 `CheckpointCorruptedError`，不捕 `ValueError` → 上抛崩溃。
- **失败场景**：检查点目录被放入 `my task.runtime.json`（含空格）或 `foo.bar.runtime.json`（含点）——手动放置、旧版本残留或文件系统损坏均可——`list_tasks()` → `load("my task")` → `_path` 抛 `ValueError` → 不被捕获 → 传播致 `python main.py tasks`（`cli.py:90`）或 WebUI `GET /api/webui/checkpoints`（`webui/api.py:102`）崩溃。
- **为何真实**：方法明确设计为"跳过损坏检查点"（`except CheckpointCorruptedError: continue` 证其意图），但最自然的损坏形式——畸形文件名——走另一异常路径不被跳过。`save()` 经 `_path` 消毒故不会自产此类文件，故现实触发概率中等，但属真实健壮性缺口。

#### P2-6 取消路径仍让 Checkpoint 卡在 `running`（声称修复的不完整覆盖）【已复验】
- **文件**：`runtime/app.py:64-108`（尤其 `:94`）、`checkpoint/models.py:40`
- **问题**：`RuntimeCheckpoint.state` 默认 `RUNNING`（`:40`），`AgentRuntime.run` 起始处保存（`:67`）。失败路径为 `except Exception as exc:`（`:94`）置 `FAILED`。但 Python 3.8+ 起 `asyncio.CancelledError` 继承 `BaseException` 而非 `Exception`（已运行验证 MRO=`[CancelledError, BaseException, object]`，非 Exception 子类）——在 `engine.run(request)`（`:76`）期间被取消时，`CancelledError` **绕过 `except Exception`**，Checkpoint 永不更新、永久 `RUNNING`。
- **失败场景**：WebUI 中用户运行任务后关闭仍在运行的服务器；`shutdown()` 取消 `run.task`（`webui/session.py:135-136`）；`CancelledError` 经 `AgentRuntime.run` 未被 `except Exception` 捕获、上至 `_execute` 的 `except asyncio.CancelledError`（`webui/session.py:184`）。**内存 WebUI 状态正确复位（"cancelled"），但持久化 Checkpoint 仍 `state=running`**——两层状态不一致。CLI 的 Ctrl+C（`asyncio.run` 取消全部任务）同理。`python main.py tasks` 随后把死运行列为"running"；`resume` 会按已存引擎/执行器/effort 重跑。
- **为何真实**：changelog 第四节声称已修"Checkpoint 永久停留在 running"（准备阶段），但取消路径的同款缺陷仍在——而 WebUI shutdown 修复（claim 5）正应覆盖"错误的运行状态"。这是本评审最具价值的符合性差异。

#### P2-7 WebUI REST `create_session` 不校验请求体形状，畸形输入致 500
- **文件**：`webui/api.py:55-68`
- **问题**：`body=await request.json()` 后 `overrides=body.get("overrides") or {}`，未校验 `body` 为 dict。客户端 POST JSON 数组/字符串，或 `{"overrides":"sequential"}`/`{"overrides":[1,2]}` 时，`.get(...)` 或 `config_schema.validate(...)`（`webui/config_schema.py:99` 调 `overrides.items()`）抛 `AttributeError`/`TypeError`。端点仅捕 `ConfigValidationError`/`ValueError`，余者上抛 500。

#### P2-8 运行时构造期的非 ValueError 异常致 500
- **文件**：`webui/api.py:62-68`、`webui/session.py:110-121`
- **问题**：`create_session`→`_runtime_factory`→`build_runtime` 可能抛 `ImportError`/`OSError`/`ConnectionError`（MCP bridge discovery、AgentBay、skills loader）。端点仅捕 `ValueError`。
- **失败场景**：用户启用某 MCP bridge 其服务器不可达；`POST /api/webui/session` 返回 500 而非结构化 422/503。`build_runtime`（`runtime/factory.py:44-51`）做网络/导入工作，仅把 `ValueError` 当可恢复过窄。

#### P2-9 评测后台任务异常被静默吞，运行卡死
- **文件**：`evaluation/server.py:35-37`
- **问题**：`spawn` 装 `task.add_done_callback(lambda done: done.exception() if not done.cancelled() else None)`。`done.exception()` 返回异常对象但 lambda 返回值被 asyncio 丢弃，无 `logger.error`。
- **失败场景**：`execute_and_save`/`generate_and_save` 抛出逃逸内部 try/except 的异常（如 `store.save_run` 磁盘满、`AttributeError` bug、`validate_repeat` 在 try 外抛——见 P3-19）→ 存储 run/evalset 永留 `RUNNING`/`GENERATING`，无错误记录无日志。用户无从得知原因。
- **为何真实**：内部 handler 覆盖正常路径，但任何意外异常被完全静默。至少应 `logger.exception(...)`。

#### P2-10 评测 Runtime/LLMClient 不关闭，大矩阵资源累积
- **文件**：`evaluation/runner.py:78`、`runtime/factory.py:203`、`llm/client.py:121`
- **问题**：每次 `evaluate_case` 新建 runtime → 新 `LLMClient` → 新 `AsyncOpenAI`（httpx 连接池）。`AgentRuntime` 无 `close`/`aclose`，`evaluate_case` 从不关闭；`finally` 的 `shutil.rmtree` 清文件沙箱但不清 HTTP 客户端。仓内 grep `def close|def aclose|__aexit__|runtime.close` 无结果。
- **失败场景**：5 cases × 3 实验 × 2 重复 = 30 单元 → 30 个 `AsyncOpenAI`。httpx `AsyncClient.__del__ 无法优雅关闭，连接池滞留至 GC 并发 `ResourceWarning`。大矩阵或对远端 LLM 反复运行可耗尽 fd/连接。
- **为何真实**：非单次崩溃，但真实资源卫生缺口，劣化长评测运行。与"WebUI 无 aclose"（见主题 T4）同源。

#### P2-11 Guardrail observe 模式把 BLOCK 降级为放行（配置相关）
- **文件**：`guardrails/engine.py:48-54`（tool-input）、`guardrails/input_guardrail.py:57-61`、`guardrails/output_guardrail.py:42-46`
- **问题**：各模式为 `"observe"` 时，BLOCK/NEUTRALIZE/REDACT 决策被降级为 ALLOW——违规作为事件发出但危险内容原样通过。tool-input 的 observe 路径尤险，因其为命令执行前最后一道。
- **失败场景**：用户开 guardrails 但设 `guardrail_tool_mode="observe"` 测试；提示注入的 `rm -r -f /`（本就绕过正则，见 P1-1）或 `/etc/passwd` 外泄企图通过并执行。
- **为何真实**：observe 为"先观测再强制"的合法模式；但 tool-input 的降级放行是会让"开了 guardrails 以为有部分防护"的操作者意外的锋利边缘。默认为强制（`block`/`neutralize`/`redact`），故配置相关、非默认。

## 四、跨切面主题（Themes）

### T1 `get_settings()` 全局单例的多处泄漏（评测隔离的潜伏陷阱）
出现于：`config.py:9`（导入期固定 + 全部别名）、`tracing/config.py:12`（导入期）、`llm/client.py:119`（`__init__` 回退）、`agents/goal_driven_planner.py:270` 与 `agents/emergent_planner.py:148`（死代码回退）。重构主体已用 `clone()`+`from_settings()` 做对隔离，但全局单例读路径散落各处。**今日多数为死代码/安全**（工厂总走注入路径），但任一外围模块读别名或直构客户端即破隔离——重构目标"评测配置隔离"在主路径达成，周边仍有泄漏面。

### T2 脱敏键集不一致（同一项目两套实现）
`tools/base.py:81`、`tracing/config.py:73`、`tracing/decorators.py:47` 用 `SENSITIVE_KEYS={"api_key","api_secret","token","password","credential","secret","authorization"}` 子串匹配，漏 `api-key`/`apikey`/`X-Api-Key`/`apiKey`/`passwd`（已运行复验）。而 `tools/subprocess_utils.py:30-36` 用正则 `api.?key`/`secret`/`token`/`password`/`credential` 正确覆盖变体。**两套实现漂移**——应统一为后者并抽公共函数，供 params/event/record/subprocess 共用。

### T3 EventBus 异步分发的"已修未竟"
changelog 第五节声称异步事件处理已修，实际：同步订阅者完全安全（所有在树订阅者皆同步，故今日无回归）；但异步分支 fire-and-forget 在 loop teardown 丢事件（P2-1）、no-loop 分支 `asyncio.run` 破共享资源（P2-2）。重构识别了问题、给了部分处理（try/except 包裹、done_callback），但未给出"await 完成"或"安全调度"的真正保证。

### T4 缺统一资源关闭接口（`aclose`/`shutdown`）
`AgentRuntime`/`RuntimeContext`/`LLMClient` 均无 `aclose`/`shutdown`。后果：评测大矩阵累积 `AsyncOpenAI` 连接池（P2-10）；WebUI 长期会话反复创建/关闭累积 httpx 连接至 GC（agent 6 注：pre-existing 设计缺口，非 shutdown 修复的回归——后者针对任务/Future/运行状态，且已正确实现）。建议为 runtime/LLM 增统一 `aclose` 并在评测每格与 WebUI 会话关闭时调用。
