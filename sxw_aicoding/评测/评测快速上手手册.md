# Manus Demo 评测快速上手手册

更新时间：2026-05-26  
适用范围：当前 `evaluation/` 评测框架，包含 v14.6 Evaluation Harness 和最新的 reasoning matrix 能力。

---

## 1. 这套评测在测什么

当前项目的评测目标不是只看“能不能跑完”，而是系统比较不同推理/规划组合在真实任务上的综合表现：

- **正确性**：任务是否成功、deterministic verifier 是否通过、pass@k 稳定性如何。
- **耗时**：端到端耗时、执行阶段耗时、P50/P95 延迟。
- **Token 成本**：总 token、prompt token、completion token、reasoning token、按 engine / caller 分桶。
- **执行质量**：工具调用成功率、ReAct 迭代数、SubAgent 成功率、HITL 调用情况。
- **可靠性**：resume 成功率、checkpoint 数、失败类型分布、回归检测。

目前主要有两类入口：

| 入口 | 用途 |
| --- | --- |
| `python3 -m evaluation.eval_cli` | 原有三种规划模式 simple / complex / emergent 的基准评测 |
| `python3 -m evaluation.reasoning_matrix` | 最新推荐入口，用于比较 ReActEngine、ReasoningEngine、effort、SubAgent、GoalDriven 等 variant |

如果你是第一次跑评测，优先从 `evaluation.reasoning_matrix` 开始。

## 3. 不消耗额度的检查

先确认评测集和 variant 是否能正常解析。这个命令不会调用真实 LLM：

```bash
python3 -m evaluation.reasoning_matrix \
  --dry-run \
  --suite smoke_reasoning \
  --variants react_auto_baseline reasoning_auto \
  --repeat 1
```

你应该看到类似信息：

```text
Suite: smoke_reasoning
Tasks (8): easy_002, easy_003, goal_easy_001, ...
Variants:
  - react_auto_baseline: modes=simple,complex,emergent ...
  - reasoning_auto: modes=simple,complex,emergent ...
```

如果 dry-run 都失败，优先修复任务 ID、suite、variant 配置，不要直接跑真实评测。

## 4. 推荐的第一次真实评测

第一次真实跑不要直接 full。建议从最小 smoke 开始：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite smoke_reasoning \
  --variants react_auto_baseline reasoning_auto \
  --repeat 1
```

这个命令会比较：

- baseline：`ReActEngine`
- candidate：`ReasoningEngine + REASONING_EFFORT=auto`

评测任务数：

- 8 个任务
- 3 个规划模式：`simple`, `complex`, `emergent`
- 2 个 variant
- repeat=1

总运行单元约为：

```text
8 tasks × 3 modes × 2 variants × 1 repeat = 48 runs
```

如果你想更省 token，可以只跑 simple：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite smoke_reasoning \
  --variants react_auto_baseline reasoning_auto \
  --modes simple \
  --repeat 1
```

## 5. 正式推理引擎对比

当 smoke 没问题后，再跑主评测：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite core_reasoning \
  --variants react_auto_baseline reasoning_auto reasoning_low reasoning_medium reasoning_high \
  --repeat 3
```

这个评测会回答几个核心问题：

- `ReasoningEngine` 是否比 baseline 更准？
- `reasoning_high` 是否值得额外 token 成本？
- `reasoning_low` 是否能在简单任务上降本？
- `reasoning_auto` 是否适合作为默认候选？

不要只看平均分，优先看：

1. `task_success_rate`
2. `verifier_pass_rate`
3. `avg_total_tokens`
4. `avg_reasoning_tokens`
5. `avg_total_wall_time_ms`
6. `failure_count`

## 6. 专项评测命令

### 6.1 评测 SubAgent / HITL / GoalDriven / Resume

```bash
python3 -m evaluation.reasoning_matrix \
  --suite agentic_capabilities \
  --variants react_auto_baseline reasoning_auto goal_driven_auto subagent_on \
  --repeat 3
```

重点看：

- SubAgent 是否真的触发。
- SubAgent 成功率是否提升最终任务成功率。
- HITL 模拟用户是否正确响应。
- GoalDriven 是否出现 `goal_anchor` / `goal_reflection`。
- Resume 任务的 `resume_success_rate`。

### 6.2 评测联网任务

```bash
python3 -m evaluation.reasoning_matrix \
  --suite live_web \
  --variants react_auto_baseline reasoning_auto reasoning_high \
  --repeat 2
```

注意：

- `live_web` 不建议和 core 混在一起下结论。
- 搜索结果、网页内容、网络状态都会漂移。
- 它适合观察工具链质量，不适合作为严格回归门禁。

### 6.3 评测 DAG 并行

```bash
python3 -m evaluation.reasoning_matrix \
  --suite core_reasoning \
  --variants react_auto_baseline dag_parallel \
  --modes complex \
  --repeat 2
```

重点看：

- complex 任务耗时是否下降。
- DAG 并发是否引入更多失败。
- token 成本是否变化。

### 6.4 全量阶段性回归

```bash
python3 -m evaluation.reasoning_matrix \
  --suite full \
  --variants react_auto_baseline reasoning_auto reasoning_medium reasoning_high \
  --repeat 3
```

这个命令成本较高，建议只在阶段性版本完成后跑。

## 7. 输出文件怎么看

每次 matrix 运行会生成：

```text
evaluation/results/<timestamp>-<suite>/
  raw_results.json
  summary.json
  summary.csv
  variant_comparison.md
  failures.md
  cost_latency.csv
  config_snapshot.json
```

### 7.1 `variant_comparison.md`

这是最适合人工阅读的总报告。

重点字段：

| 字段 | 含义 |
| --- | --- |
| `Success` | 任务成功率 |
| `Verifier` | deterministic verifier 通过率 |
| `Score` | 原有加权综合分 |
| `Tokens` | 平均总 token |
| `Reasoning Tokens` | 平均 reasoning token |
| `Calls` | 平均 LLM 调用次数 |
| `Wall Time` | 平均端到端耗时 |
| `Delta Success` | 相对 baseline 的成功率变化 |
| `Token Ratio` | 相对 baseline 的 token 倍数 |
| `Time Ratio` | 相对 baseline 的耗时倍数 |
| `Recommendation` | 自动给出的建议标签 |

常见建议标签：

| 标签 | 含义 |
| --- | --- |
| `baseline` | 当前基线 |
| `candidate_default` | 有资格作为默认候选 |
| `hard_task_candidate` | 适合 hard / emergent 专项 |
| `efficiency_regression` | 正确性无提升但成本明显升高 |
| `correctness_regression` | 成功率下降 |
| `neutral` | 暂无明显结论 |

### 7.2 `failures.md`

失败任务清单。

排查顺序建议：

1. 先看是否 verifier 明确失败。
2. 再看是否工具失败。
3. 再看是否 max iteration / timeout。
4. 最后再判断是否 benchmark 任务本身过于开放。

### 7.3 `cost_latency.csv`

适合后续用表格或 notebook 分析。

常用分析维度：

- `variant_id`
- `mode`
- `task_id`
- `success`
- `total_tokens`
- `reasoning_tokens`
- `llm_call_count`
- `total_wall_time_ms`
- `failure_category`

## 9. 旧版 eval_cli 怎么用

`eval_cli` 仍然可用，适合只比较 simple / complex / emergent 三种规划模式：

```bash

```

只跑 easy：

```bash
python3 -m evaluation.eval_cli \
  --difficulty easy \
  --modes simple \
  --repeat 1
```

输出 JSON：

```bash
python3 -m evaluation.eval_cli \
  --tasks easy_002 medium_006 \
  --modes simple complex \
  --repeat 2 \
  --output evaluation/results/manual_eval.json
```

保存 baseline：

```bash
python3 -m evaluation.eval_cli \
  --tasks easy_002 medium_006 \
  --modes simple complex \
  --save-baseline evaluation/baselines/my_baseline.json
```

对比 baseline：

```bash
python3 -m evaluation.eval_cli \
  --tasks easy_002 medium_006 \
  --modes simple complex \
  --baseline evaluation/baselines/my_baseline.json \
  --fail-on-regression
```

## 13. 如何判断一个 variant 值不值得保留

不要只按 `Score` 排名。推荐决策顺序：

1. **先看正确性**
   - `task_success_rate` 是否提升。
   - `verifier_pass_rate` 是否提升。
   - hard/emergent 子集是否明显提升。

2. **再看成本**
   - `avg_total_tokens` 是否超过 baseline 2 倍。
   - `avg_reasoning_tokens` 是否集中消耗在少数任务上。
   - easy 任务是否被 high effort 浪费。

3. **再看耗时**
   - `avg_total_wall_time_ms`
   - `p95_total_wall_time_ms`
   - 是否有 timeout 或 max iteration。

4. **最后看失败类型**
   - verifier 失败：通常是真失败。
   - tool error：优先查工具链。
   - parse failure：优先查 prompt/schema。
   - max iteration：优先查 ReAct/ReasoningEngine 收敛策略。

默认结论规则：

- 成功率没有提升，但 token 超过 baseline 1.5 倍：不建议默认启用。
- 成功率提升至少 8 个百分点，且 token/耗时都不超过 2 倍：可作为默认候选。
- `reasoning_high` 只适合 hard/emergent 有明显收益时启用。
- `live_web` 结果只作为观察，不作为严格回归结论。

## 14. 常见问题

### 14.1 `fetch_url` 相关任务大量失败

先检查：

```bash
echo $DASHSCOPE_API_KEY
```

如果没有配置，先跳过：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite core_reasoning \
  --variants react_auto_baseline reasoning_auto \
  --repeat 1
```

不要用 `live_web` 作为第一轮结论。

### 14.2 pytest 出现 `Unknown config option: asyncio_mode`

当前命令仍可用：

```bash
python3 -m pytest tests/test_evaluation_matrix.py -q -o asyncio_mode=auto
```

如果只是 warning 且测试通过，可以先忽略。后续可以补 `pytest.ini` 或对 pytest-asyncio 版本做统一。

### 14.3 评测成本太高

降低成本的顺序：

1. 加 `--modes simple` 或 `--modes complex`。
2. 把 `--repeat 3` 改成 `--repeat 1`。
3. 只跑两个 variant：`react_auto_baseline reasoning_auto`。
4. 先跑 `smoke_reasoning`，不要直接跑 `full`。

示例：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite smoke_reasoning \
  --variants react_auto_baseline reasoning_auto \
  --modes simple \
  --repeat 1
```

### 14.4 某个任务失败但看不出原因

先看：

```bash
cat evaluation/results/<run_id>/failures.md
```

再看单任务细节：

```bash
rg -n "\"task_id\": \"easy_002\"" evaluation/results/<run_id>/raw_results.json
```

重点字段：

- `final_answer`
- `verifier_details`
- `failures`
- `tokens_by_caller`
- `config_snapshot`
