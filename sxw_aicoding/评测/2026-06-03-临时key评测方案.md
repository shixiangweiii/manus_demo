# Manus Demo 临时 Key 评测方案

更新时间：2026-06-03
适用范围：基于 `sxw_aicoding/docs/operations-manual.md` 第 5 节“评测系统”，使用当前仓库 `evaluation/` 评测框架做一次临时 key 驱动的分阶段评测。

---

## 1. 目标和原则

本次评测的目标不是直接跑全量 benchmark，而是用临时 key 逐步验证：

- 评测入口是否可用。
- `react_auto_baseline` 与 `reasoning_auto` 的基础差异。
- `reasoning_low` / `reasoning_medium` / `reasoning_high` 的成本收益。
- 联网工具链 `web_search` / `fetch_url` 在配置 `DASHSCOPE_API_KEY` 后是否稳定。
- 如额度允许，再观察 `SubAgent` / `GoalDrivenPlanner` 专项能力。

执行原则：

- 使用 `python3`，不要使用 `python`。
- 不把明文临时 key 写入 `.env`、Markdown 或 git 跟踪文件。
- 默认关闭 tracing，避免 prompt / response 明文进入 trace 数据。
- 先 smoke，再 core；联网和 agentic 专项单独看，不混入核心结论。

## 3. 无成本校验

先确认 benchmark 和 matrix 配置能正常解析。这两条命令不调用真实 LLM：

```bash
python3 -m evaluation.eval_cli --dry-run
```

预期结果：

- 能渲染 benchmark 任务表。
- 当前仓库应显示约 73 个 benchmark tasks。

再检查 matrix 最小配置：

```bash
python3 -m evaluation.reasoning_matrix --dry-run \
  --suite smoke_reasoning \
  --variants react_auto_baseline reasoning_auto \
  --repeat 1
```

预期结果：

- `smoke_reasoning` 能解析出 8 个任务。
- `react_auto_baseline` 和 `reasoning_auto` 都能显示 modes / env overrides。

如果 dry-run 失败，先修复 suite、variant、任务 ID 或依赖问题，不要进入真实评测。

## 4. 第一轮低成本真实评测

先跑 smoke suite，只覆盖 `simple` 和 `complex`，控制成本：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite smoke_reasoning \
  --variants react_auto_baseline reasoning_auto \
  --modes simple complex \
  --repeat 1 \
  --output-dir evaluation/results \
  --run-id 20260603-tempkey-smoke
```

运行单元估算：

```text
8 tasks x 2 modes x 2 variants x repeat 1 = 32 runs
```

评测完成后重建对比报告：

```bash
python3 -m evaluation.compare_variants \
  --run-dir evaluation/results/20260603-tempkey-smoke \
  --baseline-variant react_auto_baseline
```

进入下一阶段的条件：

- `variant_comparison.md` 能正常生成。
- `failures.md` 中没有大面积工具初始化失败。
- 没有明显的 API key、模型名、网络认证类错误。

## 5. 核心推理对比

如果 smoke 没有严重工具链失败，再跑 core suite：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite core_reasoning \
  --variants react_auto_baseline reasoning_auto reasoning_low reasoning_medium reasoning_high \
  --repeat 2 \
  --output-dir evaluation/results \
  --run-id 20260603-tempkey-core
```

运行单元估算：

```text
20 tasks x 3 modes x 5 variants x repeat 2 = 600 runs
```

如果临时 key 额度不足，可以降级为：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite core_reasoning \
  --variants react_auto_baseline reasoning_auto reasoning_high \
  --modes simple emergent \
  --repeat 1 \
  --output-dir evaluation/results \
  --run-id 20260603-tempkey-core-lite
```

评测完成后重建报告：

```bash
python3 -m evaluation.compare_variants \
  --run-dir evaluation/results/20260603-tempkey-core \
  --baseline-variant react_auto_baseline
```

核心结论优先回答：

- `reasoning_auto` 是否可作为默认候选。
- `reasoning_low` 是否能在低成本场景保留。
- `reasoning_high` 是否只在 hard / emergent 任务上有明显收益。
- token 成本和耗时是否相对 baseline 可接受。

## 6. 联网工具专项

联网任务结果容易受搜索结果、网页内容、网络状态影响，应单独评估：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite live_web \
  --variants react_auto_baseline reasoning_auto reasoning_high \
  --repeat 1 \
  --output-dir evaluation/results \
  --run-id 20260603-tempkey-live-web
```

评测完成后：

```bash
python3 -m evaluation.compare_variants \
  --run-dir evaluation/results/20260603-tempkey-live-web \
  --baseline-variant react_auto_baseline
```

重点观察：

- `web_search` 是否走 Bailian MCP primary，失败时是否能 fallback。
- `fetch_url` 是否能通过 DashScope WebParser MCP 获取页面内容。
- `failures.md` 中是否集中出现 timeout、429、MCP transport error。

结论边界：

- `live_web` 只作为联网工具链观察。
- 不把 `live_web` 的波动直接当作 core reasoning 回归。

## 7. Agentic 专项

如果 smoke 和 core 已经通过，且临时 key 额度仍然充足，再跑 SubAgent / GoalDriven / HITL / Resume 专项：

```bash
python3 -m evaluation.reasoning_matrix \
  --suite agentic_capabilities \
  --variants react_auto_baseline reasoning_auto goal_driven_auto subagent_on \
  --repeat 2 \
  --output-dir evaluation/results \
  --run-id 20260603-tempkey-agentic
```

评测完成后：

```bash
python3 -m evaluation.compare_variants \
  --run-dir evaluation/results/20260603-tempkey-agentic \
  --baseline-variant react_auto_baseline
```

重点观察：

- `subagent_on` 是否实际触发 SubAgent。
- SubAgent 成功率是否转化为最终任务成功率提升。
- `goal_driven_auto` 是否改善 goal / condition termination 类任务。
- HITL 模拟用户是否稳定响应 `ask_user`。
- Resume 任务是否维持 `resume_success_rate`。

## 8. 输出文件和判读顺序

每轮 matrix 运行会生成：

```text
evaluation/results/<run_id>/
  raw_results.json
  summary.json
  summary.csv
  variant_comparison.md
  failures.md
  cost_latency.csv
  config_snapshot.json
```

人工判读顺序：

1. 先看 `variant_comparison.md`。
2. 再看 `failures.md`。
3. 对成本和耗时有疑问时，看 `cost_latency.csv`。
4. 需要复盘单任务细节时，看 `raw_results.json`。

核心字段：

| 字段 | 用途 |
| --- | --- |
| `Success` | 任务成功率 |
| `Verifier` | deterministic verifier 通过率 |
| `Score` | 综合评分 |
| `Tokens` | 平均总 token |
| `Reasoning Tokens` | 平均 reasoning token |
| `Calls` | 平均 LLM 调用次数 |
| `Wall Time` | 平均端到端耗时 |
| `Delta Success` | 相对 baseline 的成功率变化 |
| `Token Ratio` | 相对 baseline 的 token 倍数 |
| `Time Ratio` | 相对 baseline 的耗时倍数 |

默认决策规则：

- 成功率没有提升，但 token 超过 baseline 1.5 倍：不建议默认启用。
- 成功率提升至少 8 个百分点，且 token / 耗时都不超过 baseline 2 倍：可作为默认候选。
- `reasoning_high` 只有在 hard / emergent 明显收益时才建议保留为专项配置。
- `live_web` 结果只作为工具链观察，不作为严格回归门禁。

## 9. CI 风格基线门禁

如果需要用旧版 `eval_cli` 做 CI 风格回归检查：

```bash
python3 -m evaluation.eval_cli \
  --modes simple complex emergent \
  --baseline evaluation/baselines/v14_6_initial.json \
  --fail-on-regression \
  --output evaluation/results/20260603-tempkey-ci-results.json
```

适用场景：

- 想快速复用 `evaluation/baselines/v14_6_initial.json`。
- 只关心 simple / complex / emergent 三种规划模式的总体回归。
- 不需要 suite x variant 的细粒度对比。
